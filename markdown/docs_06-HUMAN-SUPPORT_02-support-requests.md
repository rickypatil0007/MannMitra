# Support Requests

## 1. Purpose
Defines the workflow and mechanism for students to actively request human assistance from a counsellor or the institutional support team through the MannMitra application.

## 2. Scope
Covers the creation, routing, notification, and management of support tickets/requests generated by students.

## 3. Actors
- **Student**: Initiates the request.
- **Counsellor**: Receives and responds to the request.
- **Mitra AI (Optional)**: Suggests creating a support request based on conversational context.

## 4. Requirements
- The support request form must be simple and frictionless.
- Students must have the option to attach their recent "Wellness Summary" to the request for context.
- Requests must be routed based on urgency (e.g., "General Chat" vs. "Feeling Overwhelmed").

## 5. User Flow
1. **Initiation**: Student clicks "Request Support" from the Support tab or accepts a suggestion from Mitra AI.
2. **Detail Entry**: Student selects a category (Academic, Personal, Urgent) and optionally writes a brief description.
3. **Consent Selection**: Student checks a box: "Share my 7-day stress forecast and mood trends with the counsellor."
4. **Submission**: Request is placed in the counsellor queue.
5. **Notification**: Student receives an in-app confirmation and estimated response time.

## 6. UI / UX Behavior
- **Form Design**: Minimal input fields. Large, accessible touch targets.
- **Feedback**: A clear success state confirming the request was received, with immediate access to SOS resources if they cannot wait.

## 7. Functional Behavior
- **Queueing Algorithm**: Urgent requests bypass the standard FIFO queue and are flagged for immediate triage by any available counsellor.

## 8. Data Requirements
- `SupportRequest` entity: `id`, `student_id`, `assigned_counsellor_id`, `category`, `urgency_level`, `status`, `created_at`.
- `ConsentLog`: Records exactly what data the student agreed to share at the time of the request.

## 9. Security / Privacy
- Request descriptions are considered highly sensitive and must be protected by Row Level Security (RLS) policies allowing access only to the student and the assigned counsellor.

## 10. Error Handling
- If the submission fails due to network issues, the request must be cached locally and synced when the connection is restored, notifying the user: "Your request is saved and will be sent once you are back online."

## 11. Testing
- **E2E**: Simulate a high-urgency request and verify it appears at the top of the counsellor's dashboard within 2 seconds via real-time subscriptions.
